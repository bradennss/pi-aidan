# Operate one production Minecraft host

This directory is a standalone reference, not an already deployed service. OpenTofu owns one OVHcloud US VPS, a DNS-only Cloudflare game record, and a private R2 bucket. Ansible owns the Debian 13 host, credentials, firewall, monitoring, and backup units. Kamal owns one exact upstream Minecraft **accessory**, with no app role, HTTP proxy, or custom image. Native accessory-only configuration still requires a global image field; it does not deploy that image as an app. Every lock and lifecycle command explicitly selects the single trusted `--hosts "$DEPLOY_HOST"`, including recovery/status/release. The world lives at `/srv/minecraft/worlds/primary`, independently of container removal. One host, deliberate downtime, and daily backups provide neither high availability nor zero data loss.

## Establish prerequisites

No account, order, DNS, repository setting, credential installation, notification, or deployment is performed by checks. Complete these steps only with the appropriate operational authorization.

1. Establish an OVHcloud **US** account, payment method, scoped order/cart/VPS API credentials, and independent console/rescue access. Confirm account eligibility, stock, and total cost before ordering. The public US catalog lists `vps-comfort-4-8-80`: 4 vCPU, 8 GB RAM, 80 GB NVMe, datacenter `US-EAST-VA` (Vint Hill), and OS choice `Debian 13`. The default no-commitment monthly rate is $20.00 USD before account-specific taxes/options; reconfirm it. Catalog metadata does not guarantee capacity, actual performance, or orderability. Do not substitute another location, OS, SKU, or term silently. The order uses the catalog's `vps_os` label, not a guessed image UUID. If initial access/reinstallation requires an account-specific image identifier, obtain it from that VPS's supported image API; reinstalling destroys data.
2. Establish Cloudflare DNS ownership and a dedicated private R2 bucket name. Use a scoped infrastructure API token for the selected DNS zone and R2 bucket provisioning. Create **separate host-only R2 S3 credentials**, limited to Object Read & Write on this bucket, not account administration. They do not belong in deployment or infrastructure workflows. R2 access follows token/bucket scope; test denial against other buckets during authorized commissioning. No public bucket, HTTP proxy, game TLS termination, or TCP 80/443 ingress is needed.
3. Copy this directory into a **private production repository** as its root. Protect `main` and restrict trusted operators, workflow edits, dispatch, and environment secrets. Configure `production-infrastructure`, `production-host`, and `production-game` environments with main-only deployment and approvals where the GitHub plan supports them. Record the actual protection limitations. Environment protection does **not** restrict artifact downloads: trusted repository readers can download recovery ciphertext. Public repositories are rejected by production prerequisites.
4. Set repository variable `PRODUCTION_RUNNER` to a dedicated trusted Linux x64 runner label with stable, allowlisted SSH egress. A managed static-egress offering may need a paid plan; verify availability/cost. An operator-managed runner must not run on the production VPS or be shared with PR jobs. Restrict its runner group/repository access. Empty labels fail closed; misspelled/unavailable labels can queue indefinitely. There is no broad SSH or ordinary hosted-runner fallback. Unprivileged checks use the explicitly pinned Ubuntu act runner image; **production is Debian 13**.
5. Obtain SSH host fingerprints through the independent OVH console, not unauthenticated `ssh-keyscan`. Retain an independent administrator key and a tested console/rescue path. Docker membership and passwordless sudo are root-equivalent. Restrict admin CIDRs to operator and production-runner sources, and verify the host's public interface name.
6. Follow [secret bootstrap](secrets.md#production-sops-and-age-schema), including independently escrowed age/state/restic keys. Install the environment-specific CI identities only after authorization. Never commit usable credentials, fake ciphertext, or placeholder state.

## Validate without starting a game

Install mise, Docker with Compose, Bash, and the pinned mise tools. Python is required only by native Ansible, Ruby by Kamal. There is no application package, build, or retained container test suite.

```sh
mise trust
mise install
mise exec -- just check
mise exec -- just infra-validate
mise exec -- just install-host
mise exec -- just host-check
mise exec -- just ci-test
```

`check` validates just/TOML formatting, workflow syntax and local Compose schema. Kamal 2.12.0 accepts accessory-only initialization with `servers` omitted, but its `kamal config` display crashes on that shape (`role_names` calls `nil.keys`). An empty server map is rejected for lacking a primary app role. Do not add an app-role workaround or treat help output as validation. For local native validation with fixture or protected environment inputs, use:

```sh
GEM_HOME="$(mise where gem:kamal)/libexec" mise exec -- ruby -rkamal -e \
  'Kamal::Configuration.create_from(config_file: Pathname.new("config/deploy.yml")); puts "Configuration valid"'
```

Set `GAME_VERSION`, `SERVER_IMAGE`, and the deployment schema inputs first; no EULA value is needed for configuration validation. Never print the loaded configuration/secrets. Native lock/lifecycle commands initialize and validate the same configuration before mutation. Place `--hosts` **after the subcommand**, for example `kamal lock status --hosts "$DEPLOY_HOST"`; putting it before the command can print help instead of executing it. `infra-validate` uses `init -backend=false -lockfile=readonly` and validation-only encryption input; it creates no state/resources. `host-check` is syntax-only with an empty inventory. `ci-test` runs **only** the unprivileged check job, with no secrets or production jobs. The action runtime comes from the pinned runner image; a native PATH entry preserves it for act post-actions. act cannot prove GitHub permissions, environments, concurrency, artifact access, or runner isolation. Root-repository checks do not format this example; use `just format` and review YAML/Markdown locally.

Without explicit EULA/server authorization and licensed-client access, all actual game start, protocol readiness, authenticated join, writable-world single-writer, save consistency, upgrade, failed-start recovery, and recognizable-world restore checks remain **BLOCKED/UNVERIFIED**. Native configuration, encrypted-state and filesystem checks cannot substitute for them. Do not use offline mode, bots, mock RCON, generic containers, or inherited environment values to cross that boundary.

## Provision with one serialized infrastructure writer

The manual Infrastructure workflow always uses current trusted `main`, including encrypted state. It rejects stale SHA requests, reruns, nonprivate repositories, and non-success/missing/ambiguous/gapped prior history from this exact workflow. API errors also stop it. Concurrency `production-infrastructure` is noncanceling. GitHub can replace pending runs; a canceled/gapped request conservatively requires recovery. Do not delete history, recreate the workflow, or rerun failures to reset the gate.

1. Commit real recipient rules and encrypted inputs. For workflow run number 1 only, dispatch `bootstrap` with the exact current `revision` and attestation `I reconciled cloud resources and encrypted state`. Independently establish that no resources/state need adoption. This is a checkpoint, not an apply. If it fails or history is missing, follow [infrastructure recovery](recovery.md#recover-after-an-infrastructure-failure).
2. Dispatch `plan` for review with current `main` SHA, then dispatch `apply` with the current SHA. Both require the immediately prior exact-workflow run to have succeeded. Apply creates a **fresh native-encrypted saved plan** and immediately applies it; it does not reuse a previous run's artifact. Environment approval occurs before the job, not between plan/apply. `just infra-plan` provides authorized read-only local planning, not routine local applying. There is no `infra-apply` task.
3. Wait for the entire writer to finish. It commits/pushes encrypted resulting state even after partial apply failure; the apply step remains failed. Push/API/state validation failure stops subsequent runs. A failed persistence step can retain only verified ciphertext in `encrypted-state-RUN_ID`, with **three-day retention**. No state key or plaintext plan/state accompanies it.

VPS/R2 resources have `prevent_destroy`. A plan-code change can place a replacement order; do not remove protection as an ordinary resize. State-only commits do not trigger deployment. Git and apply are not atomic: runner loss can occur after cloud mutation but before persistence/artifact upload. Native state locking is local to one runner; serialized workflow history is a conservative stop signal, not a distributed transaction. Independent inventory and break-glass reconciliation remain essential.

## Configure Debian 13 and protected administration

After authorized provisioning, use the console to establish bootstrap key access. Read the encrypted `ipv4`, `inventory`, and backup repository outputs privately through SOPS; never print full state. Populate host/deploy secrets from verified outputs and fingerprints. The host workflow creates a temporary native inventory and SSH configuration, uses an ephemeral agent, and deletes these files at exit.

Run Configure host first with `disable_bootstrap=false` and `reboot=false`. It installs Debian Docker/Compose, nftables, restic, unattended-upgrades and needrestart. Check their current Debian package versions during commissioning; developer pins do not pin distro packages. The host template owns only `table inet minecraft`, never flushes Docker's iptables-nft tables, and permits public TCP **25565 only**, established traffic, loopback/ICMP, and source-restricted SSH. The forward chain filters new public-interface DNAT traffic before Docker, including accidental non-game publications. RCON 25575 has no published port. Keep Docker's default iptables-nft backend and IPv6 bridge disabled; changes require review. Validate real IPv4/IPv6 ingress, SSH denials, Docker restart and host reboot on an authorized host. No external port test has been performed by schema checks.

Verify an independent `deploy` SSH session and `sudo -n true`, then dispatch with `disable_bootstrap=true`. The playbook independently verifies that path before disabling root/password/bootstrap login. Keep the console open until verified. Log rotation is 10 MB × 3 per container; the journal is capped at 200 MB/7 days. Server memory is 6 GiB with 1–4 GiB heap, backup 1 GiB; reserve at least 1 GiB plus actual kernel/Docker overhead on the 8 GB host and monitor pressure. Backups, restic pruning, and downloads also need disk headroom.

Security updates run automatically without automatic reboots. They may restart services. Schedule maintenance and explicitly dispatch `reboot=true` when needed. The 15-minute health timer checks root disk <85%, pending kernel restart, and failed units; failures invoke a generic HTTPS form webhook. It cannot detect total host/network loss. Arrange independent operator-selected game/host and backup-freshness monitoring. Confirm notification delivery only with authorization; no real notification is sent by local checks.

Host configuration creates `eula.env` with `EULA=FALSE` if absent and never overwrites an existing operator choice. It does not start a server or enable the backup timer by default. Do not rerun host configuration during an unresolved deployment lock/masked schedule: recover first.

## Initialize off-host backups

On the authorized host, initialize the **new** R2 repository once using the protected backup environment. Do not reinitialize a repository to hide an authentication failure. Native systemd can supply the environment without a shell loader:

```sh
sudo systemd-run --wait --pipe --collect -p EnvironmentFile=/etc/minecraft/backup.env restic init
sudo systemd-run --wait --pipe --collect -p EnvironmentFile=/etc/minecraft/backup.env restic check
```

Keep a second restic key and age/state recovery copies outside the VPS and GitHub. Prove independent recovery before retention can remove the only needed snapshot. Backups use native upstream `mc-backup now`, read-only `/data`, private RCON, file-backed passwords, and the approved `exit "$1"` post-hook after upstream save-on. No custom capture/save script is used. The unit refuses `.paused`, verifies a fresh matching snapshot and repository metadata, then retains 7 daily, 5 weekly, and 12 monthly snapshots. `keep`-tagged snapshots are retained until explicitly untagged. Retention is not a guarantee of continuous data protection; daily scheduling can lose a day's changes and failed schedules can lose more. Periodically run `restic check --read-data` and perform isolated real-client restoration.

The unit is installed in `/usr/local/lib/systemd/system`, **not** as a regular file in `/etc/systemd/system`. This deliberately allows persistent `/etc` masks to override it during upgrades. `systemctl mask` cannot normally replace a locally installed regular `/etc` unit. Do not delete units or use force flags to bypass masking failures. Inspect native `LoadState=masked` and `ActiveState=inactive`; masking alone does not stop an active backup.

## Install or deliberately upgrade

Only an operator can personally accept the EULA and edit the single `EULA` entry in `/etc/minecraft/eula.env` to `TRUE`. No workflow or inherited shell environment grants acceptance. Deployment dispatch also requires server authorization, licensed player allowlist, and matching Java/client compatibility. These prerequisites have **not** been fulfilled by this reference's validation.

Use the manual Deliberate Minecraft deployment workflow on current `main`, selecting exact vanilla `game_version`, full upstream `server_image` (`itzg/minecraft-server:RELEASE-javaMAJOR@sha256:DIGEST`), `revision`, and mode. There is no automatic main deploy, custom image build/publication, or republishing of upstream images. Verify the release and manifest digest with upstream metadata and `docker buildx imagetools inspect` first. Use `install` only for an absent owned container and genuinely empty primary world; use `upgrade` for an existing world. Restore is a separate isolated operation, never `install` over recovered/active data.

The workflow supplies an ephemeral verified SSH agent and SOPS deployment inputs, then invokes `just deploy GAME_VERSION SERVER_IMAGE MODE`. An authorized operator can invoke the same recipe inside `sops exec-env secrets/deploy.enc.yaml` with `DEPLOY_AUTHORIZED=true` and an independently prepared SSH configuration/agent. The recipe:

1. Validates exact image/game/allowlist inputs and remote explicit acceptance/storage roots, acquires the **real Kamal deployment lock**, and only then sets supported `KAMAL_LOCK=true` for its child commands.
2. Records whether the backup timer was active, stops and persistently masks that timer, and verifies the mask. For upgrade, checks fixed-name container/service-label/world ownership, synchronously completes a successful native backup, including snapshot verification. Read the backup journal and retain the snapshot ID, old exact image/game, current config revision, and intended new versions in a protected operator record. The recipe adds native restic tag `keep` to the matching pre-upgrade snapshot after masking the service, retaining it until explicitly untagged. Never log the full container inspect/environment.
3. Masks the backup **service only after** successful completion and verifies it is inactive. It never kills an in-progress capture to acquire a lock. Initial installation instead requires no owned container and an empty primary directory; it does not claim a pre-upgrade snapshot exists.
4. Explicitly stops the existing game, requires nonrunning/non-OOM exit code 0, and rejects any running container mounting the world. Only then calls native `accessory remove_container game`, scoped to stopped containers with that service label. It removes no bind data, volume, or image. Kamal boot skips any existing service-labeled container, even one renamed/stopped, so renaming is insufficient.
5. Boots the exact selected accessory image and runs bounded native `mc-monitor status` inside the existing container. Accessory boot alone does not wait for health. On success it unmasks both units, restores the previously active timer, then clears `KAMAL_LOCK` and releases the lock. For a first install the timer remains inactive until the operator enables it after client/backup verification.

Any failure intentionally leaves the manual lock and current masks in place for recovery; there is no automatic old-binary rollback. Failures before masking can leave the prior schedule unchanged. SSH/runner loss is non-atomic: inspect actual host state rather than assuming where it stopped. Inspect `kamal lock status --hosts "$DEPLOY_HOST"` and native unit/container state. Never use accessory reboot/upgrade/restart, `kamal deploy/setup/app boot`, `accessory exec` without `--reuse`, global Docker prune, or accessory remove (which can remove data) for this world. The service's restart policy is `no`; host reboot requires deliberate recovery/start, not an unreviewed second writer.

These are single-host, compliant-tool safeguards. Native masks exclude systemd starts and the manual Kamal lock excludes compliant lifecycle commands, but a root/Docker administrator can unmask units, bypass locks, mount aliases, or run another writer. They are not an adversarial isolation/distributed-lock solution. Do not overlap direct Docker, backup, host configuration, or filesystem edits with deployment.

After authorized installation, perform the [real-client persistence and restore procedure](recovery.md#verify-world-persistence-and-backup), adapted to the production game address. Inspect `docker port minecraft-game` and its bind mounts on the actual host; require only public game TCP 25565, private RCON, and one writer. Enable scheduling with `sudo systemctl enable --now minecraft-backup.timer` only after a successful capture and independent recovery. Verify timer execution, failure alerting and snapshot freshness. Downtime includes shutdown, image preparation/download and readiness; this lifecycle is neither atomic nor zero-downtime.
