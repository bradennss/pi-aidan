# Operate the stateless application

This reference deploys one disposable application container behind Kamal's HTTPS proxy on one OVHcloud US VPS in Vint Hill. OpenTofu owns the VPS and DNS, Ansible owns the Debian 13 host, and Kamal owns application containers. There is no database, application-data backup, or R2 bucket. Browser state disappears on refresh. Replacing the host can cause downtime; this is not a high-availability design.

## Validate without production access

From this directory, install the tools with mise and dependencies with `just install`. Ruby is for Kamal; the pinned Python runtime is required by Ansible, not application code. Docker, an SSH client/agent, Git, and a working shell must be installed separately. Do not install host packages or accept security prompts automatically.

```sh
just check
just build
just install-browser
just test-browser
just infra-validate
just install-host
just host-check
actionlint .github/workflows/*.yml
just test-operations
just ci-test
```

`infra-validate` uses a disposable validation passphrase, never a production key. It initializes providers without a backend and cannot provision resources. An empty-inventory Ansible syntax check is not a host test. `test-operations` uses temporary Git repositories, native-encrypted local state, and OpenTofu's built-in `terraform_data` resource to rehearse partial failure, rejected push, and reconciliation. It makes no cloud calls.

`ci-test` selects only the unprivileged `check` job. Its pinned act runner has no production secrets or Docker socket. The separate browser CI job uses the maintained Playwright image with its system libraries already installed; it does not install root packages. Run browser tests locally with the prerequisites linked in the README. act cannot establish GitHub permissions, environment approvals, runner access, concurrency ordering, registry publication, or production SSH behavior. Do not pass production secrets to act.

To check the production image directly, use native Docker and curl commands. Build with `docker build -t aidan-stateless:local .`, run it with a disposable name and a loopback-only port mapping such as `-p 127.0.0.1:4187:80`, inspect `/up` and `/`, and remove that container when done. `/up` returns `200 OK`, client routes fall back to the app, and missing `/assets/` paths return 404. TLS terminates at Kamal's proxy, not Caddy. There is no separate container test suite.

Copy this entire directory to use it independently. No parent configuration or scripts are required. Initialize a Git repository with a `main` branch before running act or Kamal commands that use Git metadata. Keep the mise configuration trusted at its new path and use frozen installs. Linux browser system libraries remain an external prerequisite.

## Prepare production prerequisites

Obtain explicit authorization before ordering, provisioning, applying, configuring a remote host, publishing, deploying, rebooting, rotating credentials, changing DNS, or sending notifications. Local validation does not authorize these operations.

1. Establish an OVHcloud **US** account, default payment method, and scoped API credentials. Confirm live US catalog eligibility, capacity, and monthly **no-commitment** pricing. `ovh-us`, subsidiary `US`, datacenter `US-EAST-VA`, OS label `Debian 13`, and plan `vps-essential-2-4-40` are the configured choices. The plan targets 2 vCPU, 4 GB RAM, and 40 GB storage. Catalog membership does not establish orderability or NVMe performance. Do not substitute a different product, region, OS, or term silently.
2. Confirm Debian 13 appears for that plan in the [public US VPS catalog](https://api.us.ovhcloud.com/1.0/order/catalog/public/vps?ovhSubsidiary=US). This configuration uses the order-time `vps_os` label, not an invented image UUID. It deliberately omits `image_id` and `public_ssh_key`: initial account-delivered access must be established through the control panel and changed to key-only access. Verify the provider's current [ordering schema](https://registry.terraform.io/providers/ovh/ovh/latest/docs/resources/vps) and required order/cart/payment permissions. If the account requires an image UUID or reinstall, obtain it from that VPS's supported images API before changing configuration; reinstallation destroys the host.
3. Delegate an owned DNS zone to Cloudflare. Create a token restricted to DNS editing in that zone. The A record is DNS-only so Kamal can obtain a certificate directly. Confirm inbound TCP 80/443, certificate challenge reachability, and any CAA constraints. No AAAA record is created.
4. Use a **private production repository** for infrastructure automation. Native Actions artifacts inherit repository-reader access, not environment approval/deploy permissions. Restrict readers to trusted operators; recovery artifacts retain native encryption and expire after three days. Public app sources and unprivileged checks are supported, but public-repository infrastructure applies need a separately agreed restricted recovery store. Do not change repository visibility automatically.
5. Protect `main` and the production environments. Limit dispatch/recovery permissions and reviews to trusted operators. Configure `production-infrastructure`, `production-host`, and `production-app` environments with branch restrictions and approvals where the repository's GitHub plan supports them. Some plans do not support the desired protection rules; document the actual restrictions before enabling automation. PR jobs must never receive production identities.
6. Ensure the repository's state-only commit policy permits the infrastructure job's `contents: write` token to persist encrypted state to `main`. Test this with authorization before the first order. If repository rules reject the push, recovery is mandatory. Do not disable branch protections broadly or assume the Actions token bypasses them. An operator-approved GitHub App/rules arrangement may be needed for a protected repository; none is provisioned here.
7. Set repository variable `PRODUCTION_RUNNER` to a trusted Linux x64 runner label with stable, allowlisted SSH egress. Prefer a supported managed static-egress runner if the account offers one. This can require a paid GitHub plan/runner and is not assumed available. An operator-managed dedicated self-hosted runner is an alternative, never installed on the production VPS and never shared with PR/build jobs. Restrict its runner group/repository access. The prerequisite jobs reject an empty variable; an unavailable or misspelled label can still queue indefinitely and must be verified by an operator. No broad SSH or ordinary hosted-runner fallback is provided.
8. Retain independent OVH console/rescue access and verify the administrative recovery path. Obtain host SSH fingerprints from a trusted console, not an unauthenticated `ssh-keyscan`. Keep an independent administrator key and age recovery identities outside the VPS and GitHub.

## Prepare secrets

Create separate age identities for state, infrastructure API, host administration, and application deployment. Keep private identities in protected local storage, with tested independent offline recovery copies. Add both each CI public recipient and the appropriate offline recovery recipient to `.sops.yaml`. Empty recipient rules intentionally cannot produce usable encrypted files. Do not reuse production identities for development.

Create each file with the native SOPS editor, for example `sops edit secrets/state.enc.yaml`, using a protected editor with swap/backup/history disabled. Store only string values. SOPS invokes the editor with temporary plaintext; use a trusted workstation and protected temporary storage. Do not paste secrets into shell history, logs, command-line arguments, or ordinary files. Never commit a private identity or a pretend ciphertext/state file.

| File | Required mapping |
| --- | --- |
| `state.enc.yaml` | `TF_VAR_state_passphrase`: independently generated high-entropy passphrase of at least 32 random bytes, retained for all state history |
| `infra.enc.yaml` | `OVH_APPLICATION_KEY`, `OVH_APPLICATION_SECRET`, `OVH_CONSUMER_KEY`, `CLOUDFLARE_API_TOKEN`, `TF_VAR_zone_id`, `TF_VAR_domain` |
| `host.enc.yaml` | `DEPLOY_HOST`, `BOOTSTRAP_USER`, `HOST_SSH_KEY` (multiline private key), `SSH_KNOWN_HOSTS` (verified complete known_hosts entry), `ADMIN_PUBLIC_KEY` (deploy public key), `ADMIN_CIDRS` (comma-separated IPv4/IPv6 administration networks), `PUBLIC_INTERFACE` (verified default-route interface), `ALERT_WEBHOOK` (HTTPS endpoint accepting form field `text`) |
| `deploy.enc.yaml` | `DEPLOY_HOST`, `APP_DOMAIN`, `REGISTRY_USER`, `KAMAL_REGISTRY_PASSWORD` (GHCR read-only credential), `DEPLOY_SSH_KEY` (multiline private key), `SSH_KNOWN_HOSTS` |

Use `tofu output -raw ipv4` through the state SOPS environment after an apply to obtain `DEPLOY_HOST`; it is not an invented address. `tofu output -json inventory` produces Ansible's supported YAML/JSON inventory structure if you need it locally. The host workflow uses the verified `DEPLOY_HOST` mapping to support initial bootstrap before the deploy user exists. Confirm it matches the current OpenTofu output before each host dispatch. Set `BOOTSTRAP_USER` to the initial account-provided user for bootstrap, then to `deploy` after access is verified. For the second run, `HOST_SSH_KEY` must match `ADMIN_PUBLIC_KEY` and authenticate as `deploy`; update both the user and key mapping if bootstrap used a different identity. CIDRs must include the production runner and operator's independently verified egress, never `0.0.0.0/0` or `::/0`. Inspect existing SSH/firewall settings before applying to an imported host.

Install only these GitHub environment secrets, with explicit authorization:

- `production-infrastructure`: `STATE_AGE_KEY` and `INFRA_AGE_KEY`. State access alone cannot call the cloud APIs; both identities are combined in memory only for plan/apply.
- `production-host`: `HOST_AGE_KEY`. No infrastructure API identity or state key.
- `production-app`: `DEPLOY_AGE_KEY`. No infrastructure API identity or state key. The image job uses only GitHub's scoped package token, not production identities.

SOPS `exec-env` passes mappings through the child's environment; no decrypted mapping is written to `GITHUB_ENV`, caches, or artifacts. SSH keys enter a temporary ssh-agent; verified known_hosts and SSH configuration files are removed at job exit. Use isolated ephemeral production runners; hard runner loss can prevent cleanup on persistent runners. `.kamal/secrets` uses SOPS's native `decrypt --extract` for the registry password. Never run `kamal secrets print` in CI or publish `kamal config` output with real credentials.

To rotate access, add new recipients and run `sops updatekeys` for each affected encrypted file, install authorized replacement CI identities, and verify recovery before revoking old access. Rotate provider/registry/SSH credentials separately. Rotating the state passphrase requires a deliberate native encryption migration retaining old decryption keys for historical state; changing the SOPS recipient alone does not re-encrypt OpenTofu state. Preserve independent historical-key recovery.

## Plan, apply, and persist state

Production applies are manual GitHub dispatches only. There is no local `infra-apply` task. `just infra-plan` is a read-only operator command requiring current configuration/state and both state and infrastructure identities, for example supplied by `SOPS_AGE_KEY_FILE`. It does not save a plan. Do not run local plans concurrently with recovery or treat a stale local plan as authorization to apply.

1. Commit real recipient rules and SOPS ciphertext, then obtain the exact current `main` SHA. For the first infrastructure workflow run, dispatch `bootstrap` on `main` with that `revision` and attestation `I reconciled cloud resources and encrypted state`. Bootstrap succeeds only as workflow run number 1 with no existing or historically committed state. Independently verify there are no resources to adopt. It records a checkpoint and never initializes/plans/applies. If bootstrap fails or history is missing, use the explicit recovery procedure rather than pretending this is a fresh environment.
2. Dispatch `plan` or `apply` on `main` with its exact current SHA, including the encrypted state commit. The workflow checks private visibility, fresh default-branch configuration, the prior exact workflow/default-branch run, and current Git history. Non-success, incomplete, missing, duplicate, or gapped history fails closed. Re-running a privileged run is rejected; dispatch a new run instead. Even a plan-only run must pass the gate. A harmless validation failure therefore also requires a recovery checkpoint.
3. Use a `plan` dispatch for review, then dispatch `apply` with the current SHA. `apply` computes a fresh native-encrypted saved plan and applies it immediately in the same job; there is no interactive approval between those steps, and environment approvals happen before the job. It does not apply a previous run's artifact. The reviewed configuration SHA is rechecked immediately before applying. The VPS has `prevent_destroy`; changing an OVH plan can order a replacement and is not an ordinary resize. Do not remove replacement protection without a separately authorized migration.
4. Wait for the run to complete. Concurrency `production-infrastructure` is noncanceling and shared by plan/apply/bootstrap/recover. GitHub may replace pending runs even with `cancel-in-progress: false`; an in-progress apply is never deliberately canceled. Such canceled/missing runs conservatively require recovery. State is committed and pushed even after partial apply failure. The apply step still fails if the operation failed. No successful checkpoint can hide a failed apply.
5. Inspect the state commit, run conclusion, and summary before another dispatch. `just persist-state` first runs `just verify-state` to verify the native encrypted envelope and confirm OpenTofu can read it under enforced encryption, then copies verified ciphertext to `.recovery/`, commits only `infra/production.tfstate`, and makes one push attempt. It never force-pushes, rebases, or retries an apply after a push conflict. State-only commits use `[skip ci]`; checks exclude that file and deploy follows successful Check runs, so they do not trigger application builds.

CI and disposable recovery rehearsals invoke the same short native-tool just recipes. The history gate remains a jq filter. Saved plans/backups stay ignored and are removed at job exit. Only verified native-encrypted state can enter the three-day recovery artifact. Repository readers can download that ciphertext; private identities and plaintext never accompany it.

## Recover after an infrastructure failure

Git and cloud operations are not atomic. A runner can disappear after resource mutation but before state persistence/upload; GitHub history is a conservative stop signal, not a distributed transaction. Do not delete failed runs, re-run them to erase their conclusion, rename/recreate the workflow to reset numbering, or prune recovery artifacts before reconciliation. Administrators can defeat the history gate by changing/deleting history or workflows. History loss, run-number gaps, and runner loss require manual inventory/reconciliation. The gate does not claim to solve this limitation.

1. Suspend new infrastructure dispatches and cancel **pending** requests, not an active apply. Wait for the active writer to finish or establish that its runner has terminated. Disable application/host workflows too if recovering the VPS. Record the failed run ID and the exact current `main` SHA.
2. Obtain the most recent encrypted state from its state commit, or download `encrypted-state-RUN_ID` from the failed run before its three-day expiry. Check artifact provenance and retain a protected copy. Compare it with current `main` and actual OVH/Cloudflare inventory using authorized read-only access. Do not assume a failed apply made no changes, or replace newer state blindly. If the artifact is absent, reconcile every resource created/changed since the last persisted state, using OpenTofu's supported import/refresh facilities under break-glass authorization. Never repeat the order to find out what happened.
3. In a fresh trusted checkout of current `main`, install the independent recovery identity, copy the reconciled ciphertext to `infra/production.tfstate`, and run `sops exec-env secrets/state.enc.yaml 'tofu -chdir=infra init -input=false -lockfile=readonly && just verify-state'`. Do not print decrypted state with `show -json` or `state pull`, upload plaintext, or commit a saved plan. Inspect lineage/serial privately if reconciliation needs them. `just verify-state` discards native `state pull` output.
4. For a rejected push with no newer state writer, carry the saved encrypted file onto fresh `main`, inspect only the intended state diff/provenance, and make a normal state-only commit. Resolve unrelated source changes separately; never merge ciphertext. If both sides changed state, stop and reconcile lineage, serial, and cloud inventory before committing. Use the protected repository's authorized state-commit path. A push conflict must never cause an automatic second apply.
5. If the very first bootstrap failed and there are genuinely no cloud resources/state, create an actual empty native-encrypted state locally under break-glass authorization with the same encryption configuration and a built-in local-only resource, remove that local-only resource with a local apply, and copy only the resulting empty encrypted state into the production checkout. It must contain no invented production resources. This is a recovery artifact created by OpenTofu, not a fabricated JSON file. If cloud resources exist, import them instead. Keep CI suspended throughout.
6. Compute `sha256sum infra/production.tfstate` (on macOS, `shasum -a 256`). Dispatch **recover**, never apply, from `main` with the exact current `revision`, encrypted file `state_sha256`, and attestation `I reconciled cloud resources and encrypted state`. This operation has only state decryption access, verifies the file and current commit/hash without plaintext output, and emits a distinct recovery checkpoint. It never plans/applies or calls the cloud APIs. A missing/unreadable state cannot be checkpointed.
7. Resume normal dispatches only after that recovery run succeeds and operators agree inventory and state match. The next apply creates a fresh plan from reconciled state. Retain the failed-run evidence and recovery keys independently.

## Configure and recover the host

After provisioning and verifying the console/fingerprint, establish key-based bootstrap access manually. Debian 13 uses its distro Docker packages (`docker.io` and `docker-cli`), nftables, unattended-upgrades, and needrestart. Check current package availability and the live default-route interface before dispatching **Configure host**. There is no Ubuntu fallback.

Run the workflow first with `disable_bootstrap=false` and `reboot=false`. It installs the deploy key, Docker log bounds, a journal cap, and security updates with automatic reboots disabled. The firewall owns only `table inet stateless`; it does not flush Docker's tables. Input allows established traffic, loopback, ICMP, source-restricted SSH, and TCP 80/443. Its forward hook runs before Docker filtering and drops other new public-interface traffic, including accidental container publications. nftables' native service persists the declarative configuration across reboots. Keep Docker's default iptables-nft backend; changing the Docker firewall backend needs a new review. Confirm rules after Docker restart, host reboot, IPv4/IPv6 connections, and an accidental non-HTTP publication on an authorized disposable host before production use.

Verify a separate deploy-user SSH session and `sudo -n true`. Then dispatch with `disable_bootstrap=true`: the playbook independently verifies that path before disabling root/password/bootstrap-user login. Ensure Debian's SSH includes the managed drop-in. Keys in the Docker group/passwordless sudo are root-equivalent; this is an administrator identity, not a sandboxed deploy account. The production runner must be trusted accordingly.

The health timer checks root-disk utilization (85% threshold), needrestart's kernel status, and failed systemd units every 15 minutes. Failure invokes a generic HTTPS form notification, without host secrets in the message. Confirm delivery with authorization; this is not an external uptime monitor and cannot report total VPS/network failure. Monitor HTTPS independently through an operator-selected service. Security upgrades may restart services; the application can be interrupted. Review pending kernel upgrades and authorize `reboot=true` during a maintenance window; unattended automatic reboots are disabled.

If SSH/firewall changes lock out administration, use the independently tested OVH console/rescue path, repair `/etc/nftables.conf` and SSH drop-ins, validate with `nft -c -f`/`sshd -t`, and restore verified admin access before rerunning Ansible. Do not permanently open SSH to the Internet. For disk alerts, inspect journals and `docker system df`, remove only known unused images/containers, and preserve retained rollback versions; do not blindly prune. For host loss, reconcile infrastructure state first, obtain separate replacement authorization, reprovision Debian 13, verify new fingerprints, rerun Ansible, and deploy the existing GHCR image. No application-data restoration is needed.

## Deploy, retry, and roll back

After Check succeeds for a trusted `main` push, Deploy serializes the complete build/deploy sequence with host configuration in group `production-app`. PR Check completions cannot enter the image/deploy jobs. The ordinary hosted image job has package-write access but no production identity. It verifies the latest non-state revision, looks up the commit tag through the registry API, and only builds on an authenticated 404. Other lookup failures stop. An existing image is reused, never republished. The image is built once for `linux/amd64` and tagged with its full commit SHA. Restrict external package writers, tag deletion, and retention so these tags cannot be altered or removed; GHCR tags are not intrinsically immutable merely because they look like SHAs.

The production runner rechecks the current target immediately before `kamal deploy --skip-push`. Kamal pulls the prebuilt image, checks `/up`, and routes HTTPS through its proxy. State-only commits are ignored when choosing the current application revision. A newer eligible main commit makes a queued older deployment fail rather than deploy stale code. A commit arriving after the final revision check can still race with an in-progress deployment; serialization ensures a newer deployment cannot finish and then be overwritten by an older queued run. No claim of atomic Git/deploy ordering is made.

Bootstrap the proxy on the configured host only after host checks and authorization. With a verified SSH config file and temporary ssh-agent loaded, use `sops exec-env secrets/deploy.enc.yaml 'kamal setup --skip-push --version=FULL_SHA'` for an already published image. Set `IMAGE_REPOSITORY` to the lowercase `owner/repository`, and `SSH_CONFIG_FILE` to your protected OpenSSH config with `StrictHostKeyChecking yes` and the verified `UserKnownHostsFile`. CI creates these files itself. Do not build on the VPS.

For a failed automatic deployment, dispatch Deploy on `main` with its current application `revision`. Manual retry **requires an existing image**; it cannot publish a missing tag. The configured app identity has only registry-read and host-admin credentials. Inspect Kamal's health/rollback output and verify public HTTPS before calling the deploy successful.

For a deliberate rollback, first suspend automatic app dispatches and wait for any active deploy to finish. Obtain explicit authorization and select a known retained version with `kamal app containers`. With the same SOPS/SSH environment, run `kamal rollback FULL_SHA`. Rollback reuses the retained image/container; it does not rebuild or overwrite the tag. If the host no longer retains that version, use `DEPLOY_AUTHORIZED=true just deploy FULL_SHA` with its existing GHCR image instead. Verify `/up`, HTTPS, and the task-list interactions, then decide whether to revert source or keep automation suspended. Resuming auto-deploy without reverting the bad main revision can redeploy it. Retained containers are bounded to three; registry retention must preserve intended recovery versions independently.
