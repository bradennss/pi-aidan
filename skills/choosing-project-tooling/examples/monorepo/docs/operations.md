# Operate the report services

One Debian 13 OVHcloud US VPS runs three independently built images from one source revision: the private Go API, private Go worker, and React assets served by authenticated Caddy. Kamal's proxy terminates public HTTPS for web only. PostgreSQL is a private accessory owned by the API configuration. OpenTofu owns VPS/DNS/R2, Ansible owns the host and backup schedule, and Kamal owns containers. All services use the native `kamal` network. The API's native network alias is `api`; no API/worker/database port is published. Only exact non-sensitive `GET /up` bypasses gateway authentication.

## Validate without production access

Use mise from this directory. Docker/Compose, Git, SSH, and a native C compiler are separate prerequisites. Ruby supports Kamal; pinned Python is Ansible's required runtime only. No parent configuration or installed dependencies are required.

```sh
just install
just check
just build
just test-integration
just test-race
pnpm exec playwright install chromium
just test-browser
just infra-validate
just install-host
just host-check
actionlint .github/workflows/*.yml
shellcheck .kamal/hooks/pre-app-boot
just test-operations
just build-images FULL_SOURCE_SHA
TEST_DEPLOYMENT_IMAGES=true TEST_IMAGE_REVISION=FULL_SOURCE_SHA just test-integration
just test-recovery
just ci-test
```

The images have distinct API/worker targets in the existing backend Dockerfile, not redundant Dockerfiles. `build-images` labels all three with the same source revision; use the actual checked-out source SHA, not a different release identity. No image is published by these commands.

Database regressions use random, guarded task-owned databases on the loopback fixture. Recovery tests use real pg_dump/restic/River and services. The opt-in image rehearsal runs the actual pre-app-boot hook with local SSH transport and host-path substitution, validates first application migration, failed additive migration, previous-image recovery, and accepted-work completion after API/worker restart. It refuses existing containers bearing production service labels. Run these tasks sequentially on a trusted disposable Docker daemon. This does not establish live SSH/Kamal/systemd/R2 behavior.

The Check workflow and `ci-test` select only unprivileged jobs. act has root-equivalent access to the local Docker daemon and must never target production. The explicitly pinned act Linux x64 runner uses host networking for PostgreSQL, with emulation on ARM. The separate browser job uses the declared Ubuntu 24.04 runner's supported Chromium libraries, checks nspr/nss prerequisites, and downloads the pinned browser without installing host OS packages. The act image can lack those libraries: that optional job must fail clearly rather than switch runners or mutate the host. Native browser checks remain available. act cannot prove GitHub permission, environment, concurrency, registry, or SSH guarantees.

Copy the entire directory outside this repository, trust its mise configuration, run frozen installs, and repeat build/integration/recovery/browser tasks. Initialize a local `main` Git repository for act/Kamal metadata. `test-operations` rehearses encrypted local state partial failure, rejected push, reconciliation, and fail-closed history without cloud access.

## Prepare production prerequisites

Obtain explicit authorization before ordering, provisioning, applying, configuring a remote host, publishing, deploying, rebooting, rotating credentials, changing DNS, or sending notifications. Local validation does not authorize these operations.

1. Establish an OVHcloud **US** account, default payment method, and scoped API credentials. Confirm live US catalog eligibility, capacity, and monthly **no-commitment** pricing. `ovh-us`, subsidiary `US`, datacenter `US-EAST-VA`, OS label `Debian 13`, and plan `vps-elite-8-16-160` are the configured choices. The plan provides 8 vCPU, 16 GB RAM, and 160 GB NVMe, meeting the 6 vCPU/12 GB/100 GB starting minimum. Exact-size 2025/2027 products are not listed for Vint Hill. The public US catalog lists this default noncommitment monthly plan at $49.50 before account-specific taxes/options; reconfirm current cost and eligibility. Catalog membership does not establish orderability or NVMe performance. Do not substitute a different product, region, OS, or term silently.
2. Confirm Debian 13 appears for that plan in the [public US VPS catalog](https://api.us.ovhcloud.com/1.0/order/catalog/public/vps?ovhSubsidiary=US). This configuration uses the order-time `vps_os` label, not an invented image UUID. It deliberately omits `image_id` and `public_ssh_key`: initial account-delivered access must be established through the control panel and changed to key-only access. Verify the provider's current [ordering schema](https://registry.terraform.io/providers/ovh/ovh/latest/docs/resources/vps) and required order/cart/payment permissions. If the account requires an image UUID or reinstall, obtain it from that VPS's supported images API before changing configuration; reinstallation destroys the host.
3. Delegate an owned DNS zone to Cloudflare. Create an infrastructure token restricted to DNS editing in that zone and R2 bucket management in the chosen account. R2 account activation and billing are explicit operator prerequisites. The bucket is private with replacement protection. Create a separate R2 Object Read & Write API token restricted to this bucket for restic, not an account-wide admin token; read/write/delete and list are needed for restore, locking, and pruning. Never give that backup identity to app or deployment jobs. No automatic R2 lifecycle expiration is configured because deleting restic chunks independently corrupts snapshots. The A record is DNS-only so Kamal can obtain a certificate directly. Confirm inbound TCP 80/443, certificate challenge reachability, and any CAA constraints. No AAAA record is created.
4. Use a **private production repository** for infrastructure automation. Native Actions artifacts inherit repository-reader access, not environment approval/deploy permissions. Restrict readers to trusted operators; recovery artifacts retain native encryption and expire after three days. Public app sources and unprivileged checks are supported, but public-repository infrastructure applies need a separately agreed restricted recovery store. Do not change repository visibility automatically.
5. Protect `main` and the production environments. Limit dispatch/recovery permissions and reviews to trusted operators. Configure `production-infrastructure`, `production-host`, and `production-app` environments with branch restrictions and approvals where the repository's GitHub plan supports them. Some plans do not support the desired protection rules; document the actual restrictions before enabling automation. PR jobs must never receive production identities.
6. Ensure the repository's state-only commit policy permits the infrastructure job's `contents: write` token to persist encrypted state to `main`. Test this with authorization before the first order. If repository rules reject the push, recovery is mandatory. Do not disable branch protections broadly or assume the Actions token bypasses them. An operator-approved GitHub App/rules arrangement may be needed for a protected repository; none is provisioned here.
7. Set repository variable `PRODUCTION_RUNNER` to a trusted Linux x64 runner label with stable, allowlisted SSH egress. Prefer a supported managed static-egress runner if the account offers one. This can require a paid GitHub plan/runner and is not assumed available. An operator-managed dedicated self-hosted runner is an alternative, never installed on the production VPS and never shared with PR/build jobs. Restrict its runner group/repository access. The prerequisite jobs reject an empty variable; an unavailable or misspelled label can still queue indefinitely and must be verified by an operator. No broad SSH or ordinary hosted-runner fallback is provided.
8. Retain independent OVH console/rescue access and verify the administrative recovery path. Obtain host SSH fingerprints from a trusted console, not an unauthenticated `ssh-keyscan`. Keep an independent administrator key and age recovery identities outside the VPS and GitHub.

## Prepare secrets

Create separate age identities for state, infrastructure API, host administration, and application deployment. Keep private identities in protected local storage, with tested independent offline recovery copies. Add both each CI public recipient and the appropriate offline recovery recipient to `.sops.yaml`. Empty recipient rules intentionally cannot produce usable encrypted files. Do not reuse production identities for development.

Create each file with the native SOPS editor, for example `sops edit secrets/state.enc.yaml`, using a protected editor with swap/backup/history disabled. Store only string values. SOPS invokes the editor with temporary plaintext; use a trusted workstation and protected temporary storage. Do not paste secrets into shell history, logs, command-line arguments, or ordinary files. Never commit a private identity or a pretend ciphertext/state file.

| File | Required mapping |
| --- | --- |
| `state.enc.yaml` | `TF_VAR_state_passphrase`: independently generated high-entropy passphrase of at least 32 random bytes, retained for all state history |
| `infra.enc.yaml` | `OVH_APPLICATION_KEY`, `OVH_APPLICATION_SECRET`, `OVH_CONSUMER_KEY`, `CLOUDFLARE_API_TOKEN`, `TF_VAR_zone_id`, `TF_VAR_domain`, `TF_VAR_account_id`, `TF_VAR_backup_bucket` |
| `host.enc.yaml` | `DEPLOY_HOST`, `BOOTSTRAP_USER`, `HOST_SSH_KEY` (multiline private key), `SSH_KNOWN_HOSTS` (verified complete known_hosts entry), `ADMIN_PUBLIC_KEY` (deploy public key), `ADMIN_CIDRS` (comma-separated IPv4/IPv6 administration networks), `PUBLIC_INTERFACE` (verified default-route interface), `ALERT_WEBHOOK` (HTTPS endpoint accepting form field `text`), plus the database and backup fields below |
| `deploy.enc.yaml` | `DEPLOY_HOST`, `APP_DOMAIN`, `REGISTRY_USER`, `KAMAL_REGISTRY_PASSWORD` (GHCR read-only credential), `DEPLOY_SSH_KEY` (multiline private key), `SSH_KNOWN_HOSTS`, `DATABASE_URL`, `POSTGRES_PASSWORD`, `BASIC_AUTH_USER`, `BASIC_AUTH_HASH` |

Host-only backup fields are `RESTIC_REPOSITORY` (the `backup_repository` OpenTofu output), `RESTIC_PASSWORD`, `AWS_ACCESS_KEY_ID`, and `AWS_SECRET_ACCESS_KEY` from the bucket-scoped backup token. Generate the restic password from at least 32 random bytes encoded as unpadded base64url (43 or more letters/digits/underscore/hyphen). Retain it and the independent age recovery keys off-host; an intact bucket without its restic password is unusable. Host `DATABASE_URL` is a duplicate of the deployment mapping, for the migration-only file; rotate both together. Use a single-line URL with a percent-encoded password, for example `postgresql://monorepo:ENCODED_PASSWORD@monorepo-api-db:5432/monorepo`, never the local fixtures. Ansible validates safe native env-file values; do not use raw quotes, whitespace, or newlines. The database password is also delivered to the PostgreSQL accessory; changing its environment does **not** rotate a password already stored in an existing PostgreSQL cluster. Coordinate an authorized PostgreSQL password change and both encrypted mappings before redeployment.

`BASIC_AUTH_HASH` comes from `caddy hash-password`, never plaintext in Git. Use a unique operator user/password. Native environment references in `.kamal/secrets` select only the registry, app database, accessory database, and gateway fields. No backup or infrastructure API credentials enter app images or deployment jobs. Host administrators remain root-equivalent and can read host backup credentials.

Use `tofu output -raw ipv4` through the state SOPS environment after an apply to obtain `DEPLOY_HOST`; it is not an invented address. `tofu output -json inventory` produces Ansible's supported YAML/JSON inventory structure if you need it locally. The host workflow uses the verified `DEPLOY_HOST` mapping to support initial bootstrap before the deploy user exists. Confirm it matches the current OpenTofu output before each host dispatch. Set `BOOTSTRAP_USER` to the initial account-provided user for bootstrap, then to `deploy` after access is verified. For the second run, `HOST_SSH_KEY` must match `ADMIN_PUBLIC_KEY` and authenticate as `deploy`; update both the user and key mapping if bootstrap used a different identity. CIDRs must include the production runner and operator's independently verified egress, never `0.0.0.0/0` or `::/0`. Inspect existing SSH/firewall settings before applying to an imported host.

Install only these GitHub environment secrets, with explicit authorization:

- `production-infrastructure`: `STATE_AGE_KEY` and `INFRA_AGE_KEY`. State access alone cannot call the cloud APIs; both identities are combined in memory only for plan/apply.
- `production-host`: `HOST_AGE_KEY`. No infrastructure API identity or state key.
- `production-app`: `DEPLOY_AGE_KEY`. No infrastructure API identity or state key. The image job uses only GitHub's scoped package token, not production identities.

SOPS `exec-env` passes mappings through the child's environment; no decrypted mapping is written to `GITHUB_ENV`, caches, or artifacts. SSH keys enter a temporary ssh-agent; verified known_hosts and SSH configuration files are removed at job exit. Use isolated ephemeral production runners; hard runner loss can prevent cleanup on persistent runners. Run every Kamal command that loads secrets inside `sops exec-env secrets/deploy.enc.yaml 'kamal ...'`; `just deploy` already supplies that child environment. `.kamal/secrets` uses native environment references so dollar characters in passwords and bcrypt hashes remain literal. Never run `kamal secrets print` in CI or publish `kamal config` output with real credentials.

To rotate access, add new recipients and run `sops updatekeys` for each affected encrypted file, install authorized replacement CI identities, and verify recovery before revoking old access. Rotate provider/registry/SSH credentials separately. Rotating the state passphrase requires a deliberate native encryption migration retaining old decryption keys for historical state; changing the SOPS recipient alone does not re-encrypt OpenTofu state. Preserve independent historical-key recovery.

## Plan, apply, and persist state

Production applies are manual GitHub dispatches only. There is no local `infra-apply` task. `just infra-plan` is a read-only operator command requiring current configuration/state and both state and infrastructure identities, for example supplied by `SOPS_AGE_KEY_FILE`. It does not save a plan. Do not run local plans concurrently with recovery or treat a stale local plan as authorization to apply.

1. Commit real recipient rules and SOPS ciphertext, then obtain the exact current `main` SHA. For the first infrastructure workflow run, dispatch `bootstrap` on `main` with that `revision` and attestation `I reconciled cloud resources and encrypted state`. Bootstrap succeeds only as workflow run number 1 with no existing or historically committed state. Independently verify there are no resources to adopt. It records a checkpoint and never initializes/plans/applies. If bootstrap fails or history is missing, use the [explicit recovery procedure](recovery.md#recover-after-an-infrastructure-failure) rather than pretending this is a fresh environment.
2. Dispatch `plan` or `apply` on `main` with its exact current SHA, including the encrypted state commit. The workflow checks private visibility, fresh default-branch configuration, the prior exact workflow/default-branch run, and current Git history. Non-success, incomplete, missing, duplicate, or gapped history fails closed. Re-running a privileged run is rejected; dispatch a new run instead. Even a plan-only run must pass the gate. A harmless validation failure therefore also requires a recovery checkpoint.
3. Use a `plan` dispatch for review, then dispatch `apply` with the current SHA. `apply` computes a fresh native-encrypted saved plan and applies it immediately in the same job; there is no interactive approval between those steps, and environment approvals happen before the job. It does not apply a previous run's artifact. The reviewed configuration SHA is rechecked immediately before applying. The VPS has `prevent_destroy`; changing an OVH plan can order a replacement and is not an ordinary resize. Do not remove replacement protection without a separately authorized migration.
4. Wait for the run to complete. Concurrency `production-infrastructure` is noncanceling and shared by plan/apply/bootstrap/recover. GitHub may replace pending runs even with `cancel-in-progress: false`; an in-progress apply is never deliberately canceled. Such canceled/missing runs conservatively require recovery. State is committed and pushed even after partial apply failure. The apply step still fails if the operation failed. No successful checkpoint can hide a failed apply.
5. Inspect the state commit, run conclusion, and summary before another dispatch. `just persist-state` first runs `just verify-state` to verify the native encrypted envelope and confirm OpenTofu can read it under enforced encryption, then copies verified ciphertext to `.recovery/`, commits only `infra/production.tfstate`, and makes one push attempt. It never force-pushes, rebases, or retries an apply after a push conflict. State-only commits use `[skip ci]`; checks exclude that file and deploy follows successful Check runs, so they do not trigger application builds.

CI and disposable recovery rehearsals invoke the same short native-tool just recipes. The history gate remains a jq filter. Saved plans/backups stay ignored and are removed at job exit. Only verified native-encrypted state can enter the three-day recovery artifact. Repository readers can download that ciphertext; private identities and plaintext never accompany it.

## Configure the host

After provisioning and verifying the console/fingerprint, establish key-based bootstrap access manually. Debian 13 uses its distro Docker packages (`docker.io` and `docker-cli`), nftables, unattended-upgrades, and needrestart. Check current package availability and the live default-route interface before dispatching **Configure host**. There is no Ubuntu fallback.

Run the workflow first with `disable_bootstrap=false` and `reboot=false`. It installs the deploy key, Docker log bounds, a journal cap, and security updates with automatic reboots disabled. The firewall owns only `table inet monorepo`; it does not flush Docker's tables. Input allows established traffic, loopback, ICMP, source-restricted SSH, and TCP 80/443. Its forward hook runs before Docker filtering and drops other new public-interface traffic, including accidental container publications. nftables' native service persists the declarative configuration across reboots. Keep Docker's default iptables-nft backend; changing the Docker firewall backend needs a new review. Confirm rules after Docker restart, host reboot, IPv4/IPv6 connections, and an accidental non-HTTP publication on an authorized disposable host before production use.

Verify a separate deploy-user SSH session and `sudo -n true`. Then dispatch with `disable_bootstrap=true`: the playbook independently verifies that path before disabling root/password/bootstrap-user login. Ensure Debian's SSH includes the managed drop-in. Keys in the Docker group/passwordless sudo are root-equivalent; this is an administrator identity, not a sandboxed deploy account. The production runner must be trusted accordingly.

The health timer checks root-disk utilization (85% threshold), needrestart's kernel status, and failed systemd units every 15 minutes. Failure invokes a generic HTTPS form notification, without host secrets in the message. Confirm delivery with authorization; this is not an external uptime monitor and cannot report total VPS/network failure. Monitor HTTPS independently through an operator-selected service. Security upgrades may restart services; the application can be interrupted. Review pending kernel upgrades and authorize `reboot=true` during a maintenance window; unattended automatic reboots are disabled.

## Deploy, retry, and recover partial releases

Deploy follows successful Check runs from trusted main pushes, never PR completions. Noncanceling `production-app` concurrency serializes publication, ordered release, and host configuration. The package-write job has no production identity. It authenticates each GHCR manifest lookup and builds only on an actual 404; 200 reuses the existing image, other statuses stop. API, worker, and web use separate repositories suffixed `-api`, `-worker`, `-web`, with the same full source SHA. Rerun a partially failed build to reuse published images and build missing ones. Manual dispatch is retry-only and requires all three existing images. No image is rebuilt on the VPS. Restrict package writers/deletion/retention because SHA-shaped tags are not registry-enforced immutability.

Both jobs reject stale application revisions, excluding only encrypted state commits. Deploy checks current main immediately before mutation. A commit after that check can still race a running deployment. A failed release is not atomic or automatically rolled back. Some images can publish without deployment; a service failure can leave API new, worker old, web old. Keep adjacent schema/API/job contracts backward compatible. Do not combine destructive migrations or changed River job arguments with service updates. The additive completion timestamp demonstrates old explicit-column inserts/reads, pending jobs, and new schema compatibility; historical completions receive migration time, not their unknown original finish time. Application rollback never undoes migrations.

Before first deploy, obtain authorization, initialize the bucket-scoped restic repository once, and configure Ansible. Protected `/etc/monorepo/migration.env` must contain only `DATABASE_URL`; R2 credentials are in a separate root-only backup file. Verify the URL uses `monorepo-api-db` and agrees with accessory credentials. Native accessory preparation creates the private network and performs registry login. Use published full-SHA images and verified ephemeral SSH configuration:

1. Run `sops exec-env secrets/deploy.enc.yaml 'kamal accessory boot db -c config/deploy.api.yml'`.
2. Poll `sops exec-env secrets/deploy.enc.yaml 'kamal accessory exec --reuse db "pg_isready -U monorepo -d monorepo" -c config/deploy.api.yml'` with a bounded deadline before continuing.
3. Run `DEPLOY_AUTHORIZED=true just deploy FULL_SHA`, with `IMAGE_REPOSITORY` set to lowercase owner/repository without service suffix, and a verified SSH agent/config. It executes API deploy (migration hook), worker deploy, then web deploy. Do not use `kamal setup` as an alternate orchestrator.
4. Verify HTTPS, unauthenticated 401 UI/API reads/writes, exact public GET /up, authenticated submission/completion, and an authorized backup/restore.

The pre-app-boot hook runs after image pull under each service's native Kamal lock. API runs goose application migrations and River native migrations in the pulled API image using the host-installed migration environment, before replacing any API/worker. This closes the genuine first-deploy image/environment gap. Failure aborts before API replacement. It then stops old APIs so private `api` DNS has no overlapping old/new backends. API binds `:8080` only inside the private runtime; the native default remains loopback. Worker deployment stops old workers gracefully and boots with proxy disabled. Web deploy is last and uses native proxy readiness. Backend downtime and gateway errors are possible. Workers can execute retries more than once; unique report-ID results prevent duplicate durable results, not external effects.

Configurations share host/network, not a distributed transaction. Per-service locks do not coordinate operators: serialize through CI, or suspend CI before authorized operator releases. Never run worker/web updates in parallel with migration. No SQL down migration, accessory reboot, or destructive rollback occurs. PostgreSQL remains on its persistent accessory volume. Ordinary deploys do not recreate accessories; PostgreSQL major upgrades need separate backup/migration approval.

For partial failure, suspend automatic deploy/host changes, inspect each exact image/schema/job health, retain the additive schema, and select a compatible image set. Worker failure after API update leaves accepted work durable in PostgreSQL. Resume the current revision to reuse images, or use [previous-image recovery](recovery.md#recover-a-failed-release). Do not promise atomic multi-service deployment or zero downtime.
